# Architecture

## Overview

The React frontend talks to the backend over HTTP with JSON. The backend stores data in SQLite and calls a text model — the Google Gemini API, a named cloud provider (Groq, OpenRouter, Mistral) or any OpenAI-compatible local endpoint (Ollama, LM Studio, llama.cpp…), switchable per story (see DECISIONS.md). In development the frontend runs on Vite (port 5173) and proxies `/api` to the backend (port 8000).

## Data models

Story: `id`, `title`, `settings` (JSON with the chosen parameters — including `age_rating`, `explicit_sexual`, `graphic_violence`, `image_style` and `narrator_style`, all absent for stories created before those fields existed, which preserves their old behavior), `status` (`active` or `finished`), `max_turns` (nullable), `pinned_facts` (JSON list of player-pinned fact notes, nullable), `created_at`, `updated_at`.

Turn: `id`, `story_id`, `index` (zero based), `player_input_type` (`option`, `custom` or `start`), `player_input_text`, `note_text` (the player's optional note to the narrator, nullable), `note_type` (the narrator's classification `fact`/`event`, nullable), `note_normalized` (the pinned formulation of a fact note, kept for exact rollback on regenerate; nullable), `narration`, `choice` (JSON, nullable at the ending), `state` (JSON), `is_ending`, `image_status` (`none`, `queued`, `generating`, `done`, `failed`; default `none`), `image_format` (always `wide` for scene illustrations — framing lives in the prompt's shot tags; `portrait` only remains in stories written before that rule, nullable), `image_prompt` (nullable), `image_path` (nullable, relative to `IMAGE_DIR`), `image_error` (nullable), `characters_in_scene` (JSON list of names, stored as canonical character names after fuzzy resolution; `__hero__` is the player character), `created_at`.

The first turn is created automatically when the story is created and has type `start`. The image columns were added to existing databases with a small startup migration (`ALTER TABLE` for any missing column), so old stories keep working.

Character: `id`, `story_id`, `name`, `is_hero`, `role`, `relationship` (to the player character), `description`, `appearance_tags`, `portrait_history` (JSON list of look versions `{appearance_tags, pose, expression, portrait_path, turn_id}`; the latest entry is the current look), `first_seen_turn_id`, `portrait_status` (same states as `image_status`; default `none`), `portrait_path`, `portrait_error`, `created_at`. One row per story and name; the hero is stored as a character row with `is_hero=true`. The table is created by the same startup migration mechanism, so existing databases upgrade in place, and rows without `portrait_history` are treated as single-version characters. Every name lookup (new-character reports, portrait updates, `characters_in_scene` canonicalization, scene tag splicing, reference portraits) goes through the shared fuzzy matcher `services/character_matching.py` — exact case-insensitive, then prefix or one-word token ("Варго" → "Капитан Варго"), then a shared lowercase descriptor token ("Тайный странник" → "Странник в чёрном") — so a re-described known character merges into its row instead of spawning a duplicate, while capitalized surnames and genitive forms ("Бабушка Лирны" vs the hero "Лирна") deliberately do not merge.

## API

`GET /api/health` returns `{"status": "ok"}`.

`GET /api/setup-options` returns the lists of settings, genres, tones, lengths, languages and cultures, plus `age_ratings` (with `default_age_rating`), `adult_genres`, `image_styles` (with `default_image_style`), `narrator_styles` (with `default_narrator_style`), `max_genres` (5) and the model list — the single source of truth for the setup screen, so lists are extended on the backend only. It also serves both text providers side by side (`default_provider`, `gemini_models`, `gemini_configured`, `local_model`, `local_configured`) so the player picks Gemini vs the local model per story; the choice is stored in the story settings as `llm_provider`. The image-style tag mappings live in backend config next to the option lists.

`GET /api/stories` returns the list of stories.

`POST /api/stories` accepts the setup parameters, creates the story, generates the first turn and returns the whole story.

`GET /api/stories/{id}` returns the story with all turns.

`PATCH /api/stories/{id}` updates the story's settings (used to change the narrator style mid-story; also backs the "Change beginning" flow while a story has only its opening turn). The same validation as creation applies (18+ flags and adult genres below 18+ are rejected with 422).

`POST /api/stories/{id}/regenerate-start` deletes the opening turn and generates it again; allowed only while the story has a single turn.

`POST /api/stories/{id}/regenerate-last` deletes the last turn and replays the stored player input (`player_input_type`/`player_input_text`, plus the stored `note_text`) to generate it again — works on finished stories too, so a bad ending can be redone (the redo is a new ending when `max_turns` is reached again). Characters first introduced on the deleted turn are removed with it (they were never met after the redo), a `portrait_update` from that turn is rolled back to the previous history entry, a fact pinned by the deleted turn's note is unpinned (matched exactly via the stored `note_normalized`) so the redo can re-pin or reclassify it, and the replaced turn's image file is deleted best-effort. Single-turn stories fall through to `regenerate-start`. Deleted rows are also removed from the in-memory `story.turns`/`story.characters` collections before regenerating — otherwise the new turn gets an off-by-one `index`.

`POST /api/stories/{id}/turns` accepts `option_id` or `custom_text` (exactly one of them, custom up to 1500 chars) plus an optional `note_text` (a "note to the narrator", up to 2000 chars), generates the next turn and returns it.

Player notes: the note never replaces the action. The turn message carries two blocks — `PLAYER FACTS` (the story's `pinned_facts`, passed in every request) and `PLAYER NOTE FOR THIS TURN` (the raw note, or `None`). The narrator classifies the note in the turn contract's service fields `note_type` (`fact`/`event`/`null`) and `normalized_text`; the backend pins a fact's normalized text to `story.pinned_facts` (deduped, latest wins, capped at 30) and treats an event as fulfilled by that same response (never pinned). A missing classification (unsupported or meaningless note) pins nothing but the note still shows in the turn history. The narrator is instructed to never mention notes or break character. The mock narrator classifies notes with a keyword heuristic (`llm.py` `_mock_extract_note`/`_mock_note_classification`), so the whole pipeline works with `MOCK_LLM=true`.

`DELETE /api/stories/{id}/pinned-facts/{index}` removes one pinned fact (the player's fix for a mistaken note) and returns the updated list.

`DELETE /api/stories/{id}` deletes the story together with its turns, then recursively deletes the story's image folder `IMAGE_DIR/{story_id}/` (scene illustrations and `char_*.png` portraits). The target path is resolved and verified to stay inside `IMAGE_DIR` before deleting; filesystem failures are logged, never fatal — a missing or locked folder still yields a 204.

`GET /api/turns/{turn_id}/image` returns `{status, format, url, error}` for the turn's illustration; `url` (under `/media/`) is set only when the status is `done`.

`POST /api/turns/{turn_id}/image/retry` re-enqueues a `failed` illustration and returns the new status; any other status is rejected with 400.

`GET /api/stories/{story_id}/characters` returns the story's characters (hero first, then by appearance) with `{name, is_hero, role, relationship, description, first_seen_turn_id, portrait_status, portrait_url, portrait_error}`; `portrait_url` is set only when `portrait_status` is `done`. `first_seen_turn_id` links a character to the turn that introduced them, so the frontend can also show their portrait inline in the turn feed at their first appearance.

`GET /api/characters/{character_id}` returns the same shape for one character.

`POST /api/characters/{character_id}/portrait` stores a player-supplied picture for a character (`{image: "data:image/…;base64,…", use_as_portrait: true}`): it is written to `IMAGE_DIR/{story_id}/photo_{character_id}.png`, kept in `Character.photo_path` and served as `photo_url`. With `use_as_portrait` it also becomes the character's current portrait immediately — status `done`, the file as `portrait_path`, one history entry — without a GPU job. A malformed upload is a 400 with a readable reason.

`POST /api/characters/{character_id}/portrait/retry` re-enqueues a `failed` portrait; any other status is rejected with 400.

Turn and story responses include `image_status`, `image_format`, `image_url` and `image_error` for every turn, so a reloaded page shows saved pictures immediately. Image files are served statically from `IMAGE_DIR` under `/media/`.

Error codes: 400 for invalid input, 404 for a missing story, 409 if the story is already finished, 422 for schema/setting validation failures (including 18+ flags or adult genres below an 18+ rating), 502 if the AI did not return a valid response after the retry, 503 if the key is not configured.

## Image generation flow

When a turn with a non-empty `image_prompt` is saved (and `IMAGE_GENERATION_ENABLED=true`), the turn is marked `queued` and its id goes into a single in-process queue. One worker thread, started at app startup, takes jobs one at a time (never two jobs on the GPU in parallel), marks the turn `generating`, and asks the local ComfyUI server. Two graphs exist, and which one is used depends on whether the player supplied pictures:

- **Edit graph** (`comfy_workflows/{wide,portrait}_edit.json`, `build_edit_workflow`) — used whenever a hero photo or a character picture exists. `image_1` is the picture being edited, `image_2..image_10` are references (one `LoadImage` per slot, linked into `TextEncodeQwenImage21`'s autogrow `images` input), and the prompt is an instruction that names the pictures (`<image1> is Mira, the main character …`) instead of a tag list — the encoder reads the pictures, so it has to be told what each one is. A scene is an edit of the hero's photo with the other people's pictures behind it and the canvas forced to the workflow's 16:9 (`custom_size`), because a photo is portrait-shaped and the picture has to be a scene, not a crop of the upload. A portrait is an edit of the picture the character already has, with the canvas following it.
- **Text graph** (`comfy_workflows/{format}.json`) — the tag-only path described above, used for every story without player pictures, so nothing changes for them. The turn ends `done` with `image_path`, or `failed` with a readable `image_error` — errors never propagate into the text flow. With `IMAGE_REFERENCE_MODE=img2img`, the current portraits of the scene's characters are uploaded to ComfyUI but drive the scene sampler only with an explicit `IMAGE_SCENE_REFERENCE=true` (tag-only is the default); without it, likeness comes from prompt text and the spliced `appearance_tags`, never from a portrait latent; turns without a finished portrait generate unchanged. With scene references opted in via `IMAGE_SCENE_REFERENCE=true`, the first in-scene portrait (hero first) is additionally wired into the first sampler through an auto-injected LoadImage → ImageScale (to the scene resolution) → VAEEncode chain with lowered denoise — a previous scene image is never fed back — but because is generated, a place the story has already left can survive into the next scene (the story walks into a hut and the picture is still a forest). When the narrator's `state.scene` names a different place than the previous turn, the place words of the previous turn's `image_prompt` that the new prompt no longer uses (at most four; a word counts as a place word when it is in `image_service.PLACE_WORDS`) are appended to the negative prompt (`previous_scene_negative`). Only the plain words are negated, never whole tags — a compound tag like `mysterious shadowy figure in black cloak between trees` also carries a character, and negating it would repaint that character. The scene-name comparison is deliberately conservative — two names sharing a word root count as the same place, so nothing is negated — and the guard never touches a scene that stayed where it was. With `GPU_VRAM_CONDUCTOR=true` (one GPU shared by Ollama and ComfyUI), the worker first asks the text server to unload its model (`keep_alive: 0`) and afterwards asks ComfyUI to free its model cache (`POST /free`) — both best-effort. On startup, turns stuck in `queued`/`generating` are reset to `failed` with "Interrupted" (the same cleanup covers `Character.portrait_status`). With `MOCK_IMAGES=true` the worker skips ComfyUI, waits ~3 s and writes a placeholder PNG, so the whole flow works without a GPU.

Prompt assembly (`assemble_positive_prompt` / `assemble_portrait_prompt` in `image_service.py`) is deterministic string building owned by the backend: the prompt opens with a rating token — `general` by default, `explicit` only for 18+ stories with `explicit_sexual` on (which is what sets the image rating; content words in the narrator's own tags are not filtered at all while filtering is off, see DECISIONS 2026-09-25). The old SDXL-era quality prefix (`masterpiece, best quality, amazing quality`) is deliberately NOT written any more: Qwen-Image-2.1 reads natural language and those tags produced the flat, oversaturated cartoon look that the user's own ComfyUI workflow does not have; the same vocabulary is still stripped out of the narrator's tags so it cannot sneak back in. After the prefix come the story's image-style positive tags (empty when the story predates `image_style`). Qwen-Image-2.1 runs the sampler at cfg=1 (the output equals the positive conditioning, there is no negative-prompt node), so style negatives and the `nsfw`/group-scene/previous-place guards computed by `negative_extra_for`/`group_scene_negative`/`previous_scene_negative` are accepted by `build_workflow` for API compatibility but intentionally not written into the workflow. The `adult` tag is enforced whenever a person tag appears, at every rating.

A frame shared by two or more characters is rewritten before assembly (`_group_scene_tags`, fed by `process_turn_image` with `max(len(characters_in_scene), spliced appearance anchors)`): `solo` and a lone `1girl`/`1boy` are dropped (they delete the other people from the picture), the count tags are written from the stored anchors (`2girls`, `1boy, 1girl`), a crop tighter than `medium wide shot` is replaced so everyone fits, and `two-shot, facing each other, looking at each other` is added — with `looking at viewer` moved into the negative prompt, so two characters never both stare into the lens. A single character in frame is left exactly as the narrator framed them.

Portraits are jobs in the same queue (one job at a time across scenes and portraits combined), always rendered with the `portrait.json` workflow (`filename_prefix=roleplaygen/story_{story_id}/portrait_{character_id}`) and saved to `IMAGE_DIR/{story_id}/char_{character_id}.png`. The portrait prompt is rating token + style tags + the character's stored `appearance_tags` + this portrait's `pose`/`expression` (narrator-supplied per portrait — including the hero's first portrait via the `hero` report — never part of the fixed appearance tags, and varied per character: stance, camera side, gaze; `full body`/`upper body` allowed inside the pose) + the framing suffix (`cowboy shot` head to thighs unless the character's own tags name a shot, `standing`/`looking at viewer` only when the narrator sent no pose at all, `simple background`). Portraits are general-rated by default (the rating token stays the backend's decision, never the narrator's), and the narrator's own nudity tags are passed through unfiltered while content filtering is off (DECISIONS 2026-09-25); a portrait is rated explicit only when the story is 18+ explicit AND the narrator tagged that look as nude (`portrait_wants_nudity`). Before a scene job is submitted, the backend appends the stored `appearance_tags` of every character in the turn's `characters_in_scene` (hero first, then in list order) AFTER the sanitized narrator `image_prompt` — the scene composition must lead because earlier tokens dominate, and leading with appearance turns a thin scene prompt into a character pin-up; appearance consistency is deterministic string assembly, not a prompt instruction the model might ignore.

Portrait evolution uses the character's `portrait_history`: a narrator `portrait_update` appends a new version, switches `appearance_tags` (scene splicing follows the new look immediately) and enqueues exactly one portrait job; `portrait_revert` makes the previous version current and points `portrait_path` at its existing file with no GPU job at all (a revert with no previous entry is ignored and logged). `portrait_status`/`portrait_error` always describe the current version. Whenever a character already has a portrait file on disk, a portrait regeneration feeds it back as the img2img reference (`_previous_portrait_reference`), so an evolving look keeps the same face instead of being repainted from tags alone; first-ever portraits stay pure txt2img.

The hero row is a character row and evolves exactly the same way: the `hero` report carries `portrait_update`/`portrait_revert` alongside `appearance_tags`/`pose`/`expression`, and `story_engine._process_character_reports` runs the same `_apply_portrait_update`/`_apply_portrait_revert` on it (translating Cyrillic tags first, as for every other character). Both flags in one turn is a contract slip: the update wins and the combination is logged. The hero's stored look is also sent back to the narrator in the `KNOWN CHARACTERS` block (`current look: ...`), because an update written from memory loses the face, hair and build the story established earlier.

## How a turn is built

The `story_engine` service assembles the context for the model: the narrator system prompt followed by the story's narrator-style fragment and AGE RATING section (both appended only when the corresponding settings exist — stories without them get the byte-identical old prompt), the story parameters, the accumulated `state.facts` from all turns without duplicates, the short `state.summary` of older turns, the full text of the last three turns (labelled as already happened, never to be replayed), the player choice, the turn number and `max_turns`, so the model knows where it is in the story. The context goes to `llm.py`, which calls the model and returns raw text. Then `story_engine` parses the JSON, validates it against the schema, checks the choice mode rules and stores the turn. On a parse or validation error it retries once, adding a description of the error to the request. A valid turn still gets one more request when its narration breaks the format rules — `services/narration_style.py` measures the answer (blank-line paragraphs, the share of words inside quotes/italics/dash dialogue, and the number of quoted exchanges crammed into a single paragraph) for turns over 700 characters, and a complaint is appended to the retry request; the second answer is stored whatever it looks like, because a formatting problem must never cost the player a turn. The same retry path carries the novelty guard `repetition_problems`, which compares the new narration against the last three turns: a re-used run of 8 words raises `REPEATED CONTENT`, a quoted line or italic thought of two words or more that comes back verbatim raises `REPEATED DIALOGUE`, and the complaint quotes the reused text so the narrator can see it. Both complaints are advice, never fatal.

Player input is also checked in `story_engine`: `option_id` must exist in the last turn, `custom_text` is allowed only when `allow_custom` is `true`, and the text length is at most 1500 characters.

## Prompts

Prompt files live in `backend/app/prompts/` as text files (the narrator system prompt and the turn message template) and are loaded by `story_engine.load_prompt`, so they can be replaced without code changes.

## Configuration

Through `.env`: `GEMINI_API_KEY`, `MODEL_NAME`, `DATABASE_URL` (default `sqlite:///./story.db`), `MAX_TOKENS` (default 4000), `MOCK_LLM`. Text provider: `LLM_PROVIDER` (`gemini` or `openai`/`local`), `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL`. Images: `IMAGE_GENERATION_ENABLED`, `COMFYUI_URL` (default `http://127.0.0.1:8188`), `IMAGE_TIMEOUT_SECONDS` (default 300), `IMAGE_DIR` (default `./data/images`), `IMAGE_STEPS` (sampler steps per image, default 25 — generation time is roughly linear in it, 16 is the practical floor for Qwen-Image detail), `MOCK_IMAGES`, `IMAGE_REFERENCE_MODE` (`off`/`img2img`), `IMAGE_REFERENCE_NODES` (comma-separated LoadImage node ids for hand-built workflows), `IMAGE_REFERENCE_DENOISE` (default 0.75), `IMAGE_SCENE_REFERENCE` (default `false`; feed the first in-scene portrait into the scene sampler as well), `GPU_VRAM_CONDUCTOR` (default `false`; unload the Ollama model before each image job and free ComfyUI's cache after it, for one shared GPU). Read in `config.py` with Pydantic Settings; every variable is documented in `.env.example` (checked by `backend/tests/test_docs_consistency.py`).

## Frontend

Story state is kept in one hook or context. The app is framed by `components/ui/AppShell`: a permanent left sidebar (the story list with a `+` button and hover-to-delete, plus the open story's character list) and a main column that each page fills. `App.tsx` owns the route, the sidebar's story list and the story tab state (`story`/`characters`, lifted up so a sidebar character click switches the tab); `StoryPage` reports the loaded cast up via `onCharactersChange`. Pages: `HomePage` (welcome panel), `SetupPage` (sectioned grid form: World / Hero / Language & culture / Narration & model / Content rating), `StoryPage`. Shared UI primitives live in `components/ui/` (`TopBar` — compact header with status dot and actions; `ChatMessage` — avatar + author + meta, or a right-aligned player bubble; `ChatInputBar` — the input row docked at the bottom). Other components: `TurnView` (one turn as chat entries, reusing the same turn data, plus the introduced/new-look portrait rows), `ImageBlock` (four states: loading placeholder with reserved aspect ratio, done with fade-in, failed with Retry, none), `IntroducedCharacters` (inline portraits under a turn's illustration for characters first seen on that turn, and — with `lookChanged` — for characters whose look changed on it, picked by `charactersWithNewLook` from the last `portrait_history` entry and labelled "New look"), `CharactersPanel` (list on the left plus a detail card on the right; polls only while a portrait is in progress), `Lightbox` (shared fullscreen overlay for every image — click to zoom between fit and actual size, closes on `Esc`, backdrop click or ✕, locks body scroll, `role="dialog"`), `ChoicePanel` (three display variants inside, one per mode, docked at the bottom of the story screen above the custom-action `ChatInputBar`), `LoadingIndicator`, `ErrorBanner`. `StoryPage` keeps its actions in the top bar: a narrator-style dropdown that PATCHes the story settings, "Change beginning"/"Regenerate opening" while only the opening exists and "Redo last turn" after that, plus Exit. The visual language is one dark near-black palette with a warm amber accent, defined as CSS custom properties (design tokens) at the top of `styles.css`. API access is in a single `api.ts` module with types that match the backend schemas. The Vite dev server proxies both `/api` and `/media` to the backend.

The turn feed scrolls automatically to the latest turn. The active choice is disabled while a request is in flight, so a turn cannot be submitted twice.
